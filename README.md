# CLI 가계부 프로그램

Python 표준 라이브러리로 구현한 터미널 기반 가계부 프로그램입니다.

거래 내역을 JSONL 파일에 저장하고, 거래 관리, 검색, 월별 통계, 예산 및 카테고리 관리, CSV 입출력 기능을 제공합니다.

## 1. 실행 환경

- Python 3.10 이상
- 외부 패키지 설치 불필요
- Python 표준 라이브러리만 사용

프로젝트 최상위 디렉터리에서 실행합니다.

```bash
python3 -m budget_app --help
```

## 2. 주요 기능

- 거래 추가, 조회, 검색, 수정, 삭제
- 날짜·카테고리·거래 유형·메모·태그 기반 검색
- 월별 수입·지출·잔액 및 카테고리별 지출 통계
- 월별 예산 설정 및 초과 경고
- 카테고리 추가·조회·삭제
- CSV 파일 가져오기 및 내보내기
- 사용자 입력 검증 및 예외 처리
- JSONL 기반 영구 저장

## 3. 사용 방법

**거래 추가**

```bash
python3 -m budget_app add
```

**최근 거래 조회**

```bash
python3 -m budget_app list --limit 10
```

**거래 검색**

```bash
python3 -m budget_app search --category food
python3 -m budget_app search --type expense
python3 -m budget_app search --q 점심
python3 -m budget_app search --from 2026-10-01 --to 2026-10-31
```

**월별 요약**

```bash
python3 -m budget_app summary --month 2026-10 --top 3
```

**예산 설정**

```bash
python3 -m budget_app budget set --month 2026-10 --amount 100000
```

**카테고리 관리**

```bash
python3 -m budget_app category list
python3 -m budget_app category add
python3 -m budget_app category remove
```

**거래 수정 및 삭제**

```bash
python3 -m budget_app update --id TX-001 --amount 20000
python3 -m budget_app delete --id TX-001
```

**CSV 내보내기 및 가져오기**

```bash
python3 -m budget_app export --out export.csv --month 2026-10
python3 -m budget_app import --from import.csv
```

**데이터 저장 폴더 변경**

```bash
python3 -m budget_app --data-dir test_data list
```

## 4. 데이터 저장 방식

기본 저장 디렉터리는 `data/`입니다.

- `transactions.jsonl`: 거래 내역
- `categories.jsonl`: 카테고리 목록
- `budgets.jsonl`: 월별 예산

JSONL 형식을 사용해 데이터를 파일에 영구 저장하며, 거래 조회에는 제너레이터를 활용합니다.

거래 ID는 `TX-001` 형식으로 생성됩니다.

CSV 파일은 다음 열을 사용합니다.

`date,type,category,amount,memo,tags`

## 5. 프로젝트 구조

- `cli.py`: 명령어 실행 분기
- `parser.py`: argparse 기반 명령어·옵션 정의
- `commands/`: 명령어별 입력·출력 및 처리
- `models.py`: 거래 데이터 모델
- `repository.py`: JSONL 데이터 저장·조회·수정
- `service.py`: 검색·통계 및 카테고리 복구
- `csv_io.py`: CSV 입출력
- `validators.py`: 입력값 검증
- `decorators.py`: 로깅 및 예외 처리
- `tests/`: 자동 테스트

## 6. 데이터 무결성 및 예외 처리

- 잘못된 날짜, 거래 유형 및 금액 입력을 검증합니다.
- 거래에서 사용 중인 카테고리는 명령어로 삭제할 수 없습니다.
- 저장된 거래에서 사용하는 카테고리가 목록에 없으면 자동으로 복구합니다.
- 저장 파일 교체가 필요한 작업에는 임시 파일과 원자적 교체 방식을 사용합니다.
- 오류 발생 시 사용자에게 메시지를 출력하고 0이 아닌 종료 코드를 반환합니다.

CSV 파일을 반복해서 가져오면 동일한 내용의 거래가 중복 저장될 수 있습니다. 또한 데이터 파일을 직접 수정하면 데이터 일관성이 깨질 수 있습니다.

### 데코레이터를 활용한 공통 기능

`decorators.py`에 다음 세 가지 데코레이터를 구현했습니다.

- `log_action`: 거래 저장·수정·삭제 시 수행한 작업을 로그로 출력
- `handle_errors`: 예외 발생 시 사용자에게 오류 메시지와 해결 힌트 출력
- `time_action`: `time.perf_counter()`를 활용하여 함수 실행 시간 측정

`time_action`은 검색 및 월별 요약 명령어에 적용하였으며, 실제 실행 결과는 다음과 같습니다.

```text
$ python3.12 -m budget_app summary --month 2026-10

2026-10 월별 요약
총 수입: 3276378원
총 지출: 75235원
잔액: 3201143원

지출 TOP 3
1. food: 75235원
[TIME] handle_summary: 0.0004s
```

실행 시간은 거래 건수와 실행 환경에 따라 달라질 수 있습니다.

### JSONL과 CSV 저장 형식 비교

| 비교 항목 | JSONL | CSV |
|---|---|---|
| 데이터 구조 | 한 줄에 하나의 JSON 객체 | 행과 열로 구성 |
| 자료형 | 숫자, 문자열, 리스트 지원 | 기본적으로 문자열 |
| 데이터 추가 | 파일 끝에 JSON 객체 추가 | 파일 끝에 행 추가 |
| 스트리밍 처리 | 한 줄씩 읽기 가능 | 한 행씩 읽기 가능 |
| 외부 프로그램 호환성 | JSON 파서 필요 | Excel 등에서 활용하기 편리 |
| 복잡한 데이터 | 태그 리스트 표현에 유리 | 리스트를 문자열로 변환해야 함 |

**JSONL 선택 이유**

거래 데이터는 날짜, 거래 유형, 카테고리, 금액뿐 아니라 여러 개의 태그를 포함합니다.

JSONL은 하나의 거래를 JSON 객체로 표현할 수 있고, `tags`를 리스트 형태로 저장할 수 있어 데이터 구조를 유지하기 편리합니다.

또한 데이터를 한 줄씩 읽을 수 있으므로 제너레이터를 활용한 스트리밍 처리에 적합합니다.

따라서 내부 영구 저장에는 JSONL을 사용했습니다.

**CSV 사용 이유**

CSV는 표 형태의 데이터를 Excel 등 외부 프로그램과 쉽게 교환할 수 있다는 장점이 있습니다.

따라서 내부 저장에는 JSONL을 사용하고, 외부 데이터 가져오기와 내보내기에는 CSV를 사용하도록 역할을 분리했습니다.


## 대용량 데이터 처리 시 병목 분석 및 개선 방안

현재 프로그램은 JSONL 파일에 거래 내역을 저장하고, 제너레이터를 활용해 데이터를 순차적으로 읽도록 구현했습니다.

거래가 100,000건 저장된 상황을 가정하여 주요 기능의 시간복잡도와 병목 지점을 분석했습니다.

### 1. 기능별 성능 분석

| 기능 | 현재 구현 방식 | 시간복잡도 | 병목 및 개선 방안 |
|---|---|---|---|
| 거래 목록 조회 | 제너레이터 + `heapq.nlargest()` | O(N log K) | 날짜 인덱스 도입 |
| 거래 검색 | 모든 거래를 순차 탐색 | O(N) | 날짜·카테고리별 인덱스 도입 |
| 월별 요약 | 전체 거래 순회 및 합산 | O(N) | 월별 합계 캐시 활용 |
| 거래 수정·삭제 | 전체 JSONL 파일 재작성 | O(N) | 데이터베이스 전환 |
| ID 생성 | 전체 거래를 읽어 최대 ID 확인 | O(N) | 마지막 ID 별도 관리 |
| CSV 가져오기 | 거래마다 ID 조회 및 개별 저장 | 반복적인 O(N) 탐색 | ID 일괄 발급 및 배치 저장 |
| 카테고리 자동 복구 | 실행할 때마다 거래 전체 검사 | O(N) | 필요할 때만 검사 |

N은 전체 거래 건수, K는 조회할 거래 건수를 의미합니다.

### 2. 예상되는 주요 병목

**① 거래 수정 및 삭제**

JSONL은 기존 파일 끝에 새로운 거래를 추가하기는 쉽지만, 특정 거래를 수정하거나 삭제하려면 전체 파일을 순회하며 새로운 파일을 작성해야 합니다.

현재는 임시 파일을 작성한 뒤 `os.replace()`로 교체하므로 안전성을 확보했지만, 거래가 많아질수록 파일 입출력 비용이 증가합니다.

**② CSV 대량 가져오기**

현재 순차 ID 생성 함수는 저장된 거래 전체를 탐색해 가장 큰 번호를 확인합니다.

따라서 CSV 파일의 각 거래마다 ID를 새로 생성하면 반복적인 파일 읽기가 발생합니다.

예를 들어 기존 거래가 100,000건이고 CSV 거래 1,000건을 가져온다면, 기존 거래를 반복해서 읽는 작업만으로 약 1억 건 이상의 레코드 확인이 발생할 수 있습니다.

이를 개선하기 위해 가져오기 시작 시 최대 ID를 한 번만 계산하고, 이후에는 메모리에서 번호를 증가시키는 방식을 고려할 수 있습니다.

**③ 월별 통계와 검색**

제너레이터를 이용하므로 전체 거래를 리스트에 저장하지 않고 처리할 수 있습니다.

그러나 특정 월이나 카테고리의 거래를 조회하더라도 모든 거래를 확인해야 하므로 데이터가 증가하면 응답 시간이 길어집니다.

월별 합계를 별도로 관리하거나 인덱스를 구축하면 탐색 범위를 줄일 수 있습니다.

### 3. 개선 방향

단기적으로는 CSV 일괄 저장, 순차 ID 생성 최적화, 카테고리 검사 빈도 감소를 고려할 수 있습니다.

장기적으로 거래량이 증가하면 JSONL 대신 SQLite를 도입하여 인덱스 검색, 트랜잭션 처리, 데이터 수정·삭제 효율을 개선할 수 있습니다.

현재 구현은 외부 의존성을 최소화하고 파일 처리, 제너레이터, 예외 처리, 원자적 저장을 학습하는 데 목적을 두었습니다.

※ 위 내용은 코드 구조에 따른 시간복잡도 분석이며, 실제 100,000건 데이터를 이용한 벤치마크 측정 결과는 아닙니다.

### CSV 가져오기 원자성 및 롤백 정책

CSV 가져오기는 `save_many_atomic()`을 이용해 기존 거래와 새 거래를 임시 JSONL 파일에 기록합니다.

모든 파일 읽기·쓰기 작업이 완료되면 `os.replace()`를 이용해 원본 파일을 교체합니다. 처리 중 예외가 발생하면 임시 파일을 삭제하고 기존 거래 파일을 유지합니다.

- 정상 행: 가져오기 대상에 포함
- 검증에 실패한 행: 건너뛰고 `skipped` 증가
- 파일 읽기·쓰기 등 처리 중 예외: 가져오기 작업 취소 및 기존 파일 유지
- 정상적으로 처리된 행: 하나의 파일 교체 작업으로 일괄 반영

이 방식으로 가져오기 도중 오류가 발생했을 때 일부 거래만 저장되는 문제를 방지합니다.

단, 동시에 여러 프로세스가 동일한 거래 파일을 수정하는 상황까지 보장하지는 않습니다. 파일 잠금 등의 동시성 제어는 향후 개선 사항입니다.
